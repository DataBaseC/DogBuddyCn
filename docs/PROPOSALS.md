# DogBuddyCn 设计优化方案（供决策）

> 2026-10-14 ｜ 对应版本 0.3.1 ｜ 本文只提"分叉路口"的方案对比，执行清单见 ROADMAP.md
> 每个议题给了选项、成本、推荐。**选定后我再出对应的技术方案与排期。**

## 现状一句话

骨架扎实（五层架构/工位会话/抗损压缩/自更新/迁移机制），短板集中在**实时交互、产品化体验、
信任闭环**三处；ROADMAP 的 P0~P2 是"修什么"，本文回答"往哪个方向修"。

---

## 议题 1｜产品定位（最重要，决定其他一切）

| 选项 | 内涵 | 成本 | 风险 |
|------|------|------|------|
| **A. 个人数字员工团队** | 单用户极客工具，做深"无人值守编程代理"：更强的长任务、更好的信任控制、更深的工位记忆 | 低（现状延长线） | 用户圈小 |
| **B. 通用 Agent 平台** | 多租户、插件市场、可托管给别人用，向开源社区生长 | 高（鉴权/隔离/生态全要重做） | 战线过长，两头不靠 |
| **C. 垂直成品：QQ 驱动的服务器管家** | 收窄卖点，把"QQ 说一句话→服务器上的活干完"做到极致顺滑，面向中文站长/运维 | 中（砍掉泛化、打磨单场景） | 放弃"数字团队"叙事 |

**推荐：A 为体、C 为皮。** 内核继续按"个人数字团队"演进（保住架构优势），但产品叙事、
README、控制台文案、默认配置向 C 的场景收敛（"你的 QQ 服务器管家"），降低新用户理解成本。
B 不建议现在做——多租户是不可逆的架构分叉，等有真实第二个用户再说。

---

## 议题 2｜前端技术路线（ROADMAP P2 悬置项）

| 选项 | 内涵 | 成本 | 收益 |
|------|------|------|------|
| **A. 零构建 + 工程化补强** | 保持原生 JS，加 JSDoc 类型注解 + tsc --noEmit 检查 + ESLint + 版本指纹（?v=） | 1~2 天 | 消灭"低级 JS 错误"，保留零构建部署优势 |
| **B. Vite + Vue3/React 重写** | 5.7k 行全量重写 | 2~3 周 | 组件化、状态管理、生态；但引入 node 构建链，与"离线 wheels/简单部署"的调性冲突 |
| **C. 渐进混合** | 壳与新视图用构建产物，旧视图渐进迁移 | 长期 | 两套体系并存的维护税 |

**推荐：A，12 个月内不碰 B。** 本项目核心竞争力在 agent 侧而非前端；当前面板 7 个视图的复杂度
原生 JS 完全扛得住（真实痛点是缺类型检查和缓存指纹，不是缺框架）。若未来交互复杂度翻倍
（如实时画布、复杂表格编辑），再议 B。

---

## 议题 3｜实时交互层（P0-2.4 + P1-3.1 是同一问题）

| 选项 | 内涵 | 成本 | 判断 |
|------|------|------|------|
| **A. SSE（Server-Sent Events）** | 单向事件流推浏览器：工位状态/任务运行/限速/升级进度/对话打字机 | 低（FastAPI 原生支持、断线自动重连、代理友好） | **够用** |
| **B. WebSocket 双向** | 全双工：事件推送 + 浏览器直发指令 + 流式对话 | 中（连接管理/心跳/重连/多标签一致性） | 除非要做浏览器端实时协同编辑 |
| **C. 轮询改良** | 缩短间隔 + ETag | 极低 | 治标不治本 |

**推荐：A。** 浏览器侧的"实时"95% 是看，1% 是发指令（REST 就够），4% 是流式文本（SSE 天生擅长）。
SSE 一个通道同时解决 P0-2.4 和 P1-3.1（对话流式），成本约 2~3 天。
实施要点：`GET /api/events`（鉴权头）复用 EventBus 订阅；前端 EventSource + 指数退避重连。

---

## 议题 4｜Agent 交互质量（流式 + 工具可观测 + ask_user 闭环）

这不是"要不要"而是"做多深"。三档：

| 档位 | 内容 | 成本 |
|------|------|------|
| **浅** | DTO 带 tool_name/耗时（P0-2.2）+ 流式只透传最终回复文本 | 2 天 |
| **中（推荐）** | 浅档 + AgentLoop 逐轮推送"正在执行 xxx 工具"事件（SSE）+ ask_user 阻塞回路（问题→通知→等待答复→回填会话，含超时与"拒绝"选项） | 1 周 |
| **深** | 中档 + 思考链展示 + 工具参数实时展开 + 干跑预演（PLAN 模式可视化） | 2 周+ |

**推荐：中档。** "看着它干活 + 卡住了能问你 + 你的回答能进回路"是无人值守代理的信任基石；
思考链展示性价比低（模型不提供真思考链时是表演）。

**ask_user 回路设计要点**（无论选哪档都建议照此做）：
问题落 `pending_questions` 表 → SSE 通知 + QQ 推送 → 管理员/web 可"回答/拒绝/让我看看"→
答案以 `context_inject` 回填 → 工位下次运行自动携带。任务不挂死：设默认超时（如 24h）后带
"未获答复"标记继续。

---

## 议题 5｜多用户与权限（P1-3.8）

| 选项 | 内涵 | 成本 |
|------|------|------|
| **A. 现状维持** | whitelist.role 仅标记，人人同权 | 0 |
| **B. 实权分级（推荐）** | owner（全权）/ admin（管工位任务）/ viewer（只读面板）三级；工具层按 role 裁决；工位归属字段预留 | 3~4 天 |
| **C. 多租户** | 组织/团队/隔离工作区/计费 | 数周，架构分叉 |

**推荐：B。** 成本低、直接兑现 v1.3 预留的 role 字段，且是通往 C 的干净台阶（B 不做直接上 C 会返工）。
配合议题 1 的定位，viewer 级"给家人/朋友看一眼"的场景很自然。

---

## 议题 6｜技能/插件生态（P1-3.5/3.6/3.7）

| 选项 | 内涵 | 判断 |
|------|------|------|
| **A. MCP 优先** | 能力层直接接 MCP server（借现成生态：文件系统/Git/浏览器…） | 工具面暴涨，但 MCP 是"工具"不是"工作流" |
| **B. 原生 skills 优先** | 自定义 SKILL.md + 工具包加载（类 Claude skills） | 表达力强，但生态从零 |
| **C. 双轨分层（推荐）** | **MCP = 能力供给**（ToolRegistry 挂 MCP bridge，一个注册点）；**skills = 编排资产**（SOP/提示词/工具组合，目录即插件） | 各取所长 |

**推荐：C，先 MCP bridge 后 skills 加载。** MCP bridge 是纯 L4 增量（一个适配器 + 注册），
半天级；skills 等有 3 个以上真实复用场景再定格式（避免设计空格式——ROADMAP 已经踩过
`skills.py` 空壳的坑）。

---

## 议题 7｜信任模型（无人值守的护城河）

现状：三模式 + 黑名单 + 定时禁 AUTO。建议演进为**四级信任 + 审批回路**：

| 级别 | 权限 | 场景 |
|------|------|------|
| PLAN | 只读规划 | 默认入局 |
| BUILD | 工作区读写 + 危险命令需确认 | 日常 |
| AUTO | 全放行（含工作区外写） | 手动会话 |
| **ELEVATED**（新增） | 经你逐条批准的"放行清单"生效 | 夜间定时任务跑高危动作 |

配套：**审批回路**复用议题 4 的 ask_user 管道（"任务想 `systemctl restart nginx`，批不批？"→
QQ 一键批准→记入该工位放行清单+审计）。这是"没人值守也敢让它干活"的关键一步，
也是和同类产品拉开差距的点。成本约 1 周（管道复用后）。

---

## 三档组合（如果不想逐项选）

| 组合 | 选型 | 总成本 | 适合 |
|------|------|--------|------|
| **稳健档** | 1A · 2A · 3A · 4浅 · 5A · 6A · 7 不动 | ~2 周 | 先把 P0 修完再说 |
| **进取档（推荐）** | 1A体C皮 · 2A · 3A · 4中 · 5B · 6C · 7 四级信任 | ~5~6 周 | 产品感与内核同步升级 |
| **野心档** | 1B · 2B · 3B · 4深 · 5C · 6C · 7 完整审批流 | 3 个月+ | 冲开源平台 |

**推荐进取档**，理由：每一步都在现有架构延长线上（无推倒重来），且 ROADMAP 的 P0/P1 正好
被吸收进对应议题（P0-2.2/2.3/2.4 → 议题 3/4；P1-3.1/3.4 → 议题 3/4；P1-3.7/3.8 → 议题 5/6），
不存在"方案与欠账打架"。

# 补充议题（用户反馈 2026-10-14）

## 议题 8｜压缩阈值等工位级参数（痛点：自动压缩触发大小调不了）

**现状**：`compact_threshold`（80%）、`max_context_tokens` 是全局配置，所有工位一刀切；
工位详情没有参数页。这正是 ROADMAP P0-2.3。

| 选项 | 内涵 | 成本 |
|------|------|------|
| **A. 只做压缩两项** | 工位级覆盖 compact_threshold + max_context_tokens，其余不动 | ~1 天 |
| **B. 一次做全套覆盖机制（推荐）** | 机制做成通用"工位参数覆盖表"：compact_threshold / max_context_tokens / temperature / max_iterations / request_timeout / retry.* 全部工位级可覆盖，UI 显示"继承中/已覆盖"+一键还原 | 2~3 天 |

**推荐 B**：机制成本一样，字段是白送的，避免"再修三次同类问题"。落地要点：
- `windows` 表加 `params_json` 覆盖列（NULL=全继承），走 `_MIGRATIONS`
- 解析链统一进 `AppConfig.effective_*(window)`：**工位覆盖 → 绑定 profile → active profile → 全局默认**
  （v1.3 的 model 解析链扩成一张表，消除 ROADMAP"两套覆盖机制"的坑）
- 工位详情加"参数"标签：分组显示继承来源，改完即刻生效（下一次运行用新值）
- 压缩行额外给两个展示：当前上下文用量进度条 + "立即压缩"按钮（已有 API）

## 议题 9｜能力可发现性（痛点：新用户不知道系统能干什么）

**现状**：能力藏在管理员工具包里，README 之外无处可查。

| 选项 | 内涵 | 成本 |
|------|------|------|
| **A. 能力清单页** | 面板新增"能力"视图：工具卡片（名称/说明/权限级/所属角色）+ 角色能力矩阵 + 调度格式/回报策略/权限模式速查。数据源=ToolRegistry.schemas()+RoleSpec（后端 `GET /api/capabilities` 聚合） | ~1 天 |
| **B. 管理员主动引导** | 管理员会话首条消息发能力菜单；识别"你能做什么"类问题返回能力目录（提示词+能力 API 复用） | ~0.5 天 |
| **C. 对话快捷指令** | web 对话框 `/` 唤起能力目录，点选即插指令模板（如 `/建工位`） | ~1 天 |

**推荐 A+B 立即做，C 跟随**。A 是静态真相源（工具注册处自动同步，永不漂移），B 让 QQ 用户也能发现，
C 是锦上添花。关键设计：能力清单**从注册表自动生成**，新增工具自动上架，杜绝文档漂移。

## 议题 10｜群组协作：几个员工拉一起干活（原设计承诺未兑现）

**目标**：多个员工围绕同一个项目/目标协同工作。

| 选项 | 形态 | 成本 | 风险 |
|------|------|------|------|
| **A. 共享工作频道（推荐先行）** | 群组=共享上下文+共享待办+产出汇聚：建组时选成员，组员按序/按分工在**同一份共享上下文**上接力干活，产出进频道；可指定组长收尾汇总 | 1.5~2 周 | 低：复用现有会话引擎+串行队列，只是把"一人窗口"扩成"一组共享窗口" |
| **B. 主从编排（A 的升级）** | 组长（coordinator）拆解目标→派子任务给组员（复用 dispatch）→收结果汇总→迭代 | +1~2 周 | 中：需要子任务派发与汇总循环，token 成本上升 |
| **C. 自由多智能体会话** | 组员在同一频道互相 @ 自由讨论（ChatDev/MetaGPT 式） | 3~4 周 | 高：烧 token、收敛不可控、调试地狱 |

**推荐 A 先行、B 演进、C 不做。** A 已完整兑现"拉在一起干活"（有组、有频道、有共享上下文、
有汇总产出），且是 B 的干净地基；C 的投入产出比差。
A 的落地骨架：
- 表：`groups(id,name,goal)` + `group_members(group_id,window_id,role)` + 消息表加 `group_id`
- 任务：`task_create(group_id=...)` → 组员按分工（或轮序）在共享上下文执行，中间产出落频道
- UI：群组视图（成员卡 + 共享频道时间线 + 组任务 + "汇总报告"）
- 权限/模式：取组员中**最严**模式（安全优先）
