# 工业 AI 流水线自动化 · 设计（v0.11 → v0.13）

> 状态：**已立项，待动工**（2026-10-25 立）。本文是设计基线；实现进度与服务端事实以 `ROADMAP.md` 为准。
> owner 定调：后期开发偏向**工业 AI 流水线自动化**（如检测成本智能调度），并可能延伸到**让 AI 运营一个网站/项目**。
> 两条线**共用同一底座**，业务差异做成插件，不重复造轮子。

---

## 0. 一句话定位

> **DogBuddy 不做产线控制，做"编排 + 成本/质量决策 + 可追溯"。**

边缘负责取图与动作（PLC/相机/网关），DogBuddy 负责：把检测流程拆成可续跑的步骤、在预算与质量约束下决定"用哪个模型、要不要复核、要不要停"，并把每一步的**钱、结果、人、证据**全部留痕。

明确不做（见 §8）：硬实时控制、像素级判定（交给专用 CV 模型）、图像上云。

## 1. 为什么先做成本（有数据支撑）

2026-10-22～24 的生产遥测证明：**系统对"单位任务成本"没有数字**。

| 观测 | 数字 | 说明 |
|---|---|---|
| 4 天压缩次数（3 工位） | **94 次** | 每次 = 一次摘要调用 + 前缀重写（缓存全废） |
| 压缩降级率 | **19 / 99 = 19%** | 全是 TimeoutError，降级 = 原文截断 |
| 缓存命中 | 10-23 仅 **11.5%** | 与压缩同源：压缩越勤，前缀越碎 |
| 现有成本能力 | 只有 `messages.tokens` 求和 + 时间预算（`task_timeout` / `DELEGATE_SETTLE_BUDGET`） | **没有单价、没有逐任务归集、没有"质量地板"** |

「检测成本智能调度」的本质是 **在一个成本函数 + 一个质量约束下做决策**。成本不可观测时，任何"智能调度"都是拍脑袋。所以路线图第一步不是调度算法，是把钱变成数字。

## 3. 数据模型（目标 schema 16，分两次迁）

```sql
-- A1 单价表：单价可改，历史按当时价结算
CREATE TABLE cost_model(
  id TEXT PRIMARY KEY,            -- provider:model[:端点host]
  provider TEXT DEFAULT '', model TEXT NOT NULL,
  unit TEXT DEFAULT 'token',      -- token | image | minute
  in_price REAL DEFAULT 0,        -- 每 1K input token / 每张图 / 每分钟
  out_price REAL DEFAULT 0,
  cache_price REAL DEFAULT 0,     -- 命中缓存的 input 单价（部分厂商更便宜）
  currency TEXT DEFAULT 'CNY',
  effective_from TEXT DEFAULT '', note TEXT DEFAULT '',
  enabled INTEGER DEFAULT 1, updated_at TEXT DEFAULT ''
);

-- A2 账本：一次外部调用（LLM/视觉/工具）一行
CREATE TABLE usage_ledger(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts TEXT NOT NULL,
  kind TEXT DEFAULT 'llm',        -- llm | vision | tool
  run_id TEXT DEFAULT '', job_id TEXT DEFAULT '', group_id TEXT DEFAULT '',
  window_id TEXT DEFAULT '',      -- admin:default / 工位 id
  provider TEXT DEFAULT '', model TEXT DEFAULT '',
  in_tokens INTEGER DEFAULT 0, out_tokens INTEGER DEFAULT 0,
  cache_hit_tokens INTEGER DEFAULT 0, images INTEGER DEFAULT 0,
  unit_price REAL DEFAULT 0, amount REAL DEFAULT 0,
  idem_key TEXT DEFAULT '',       -- 幂等：重复上报不重复计费
  meta_json TEXT DEFAULT ''
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_ledger_idem ON usage_ledger(idem_key) WHERE idem_key<>'';
CREATE INDEX IF NOT EXISTS ix_ledger_ts ON usage_ledger(ts);
CREATE INDEX IF NOT EXISTS ix_ledger_scope ON usage_ledger(window_id, run_id);

-- A3 预算：三级（global / group / job），日或周
CREATE TABLE budgets(
  id TEXT PRIMARY KEY, scope_type TEXT NOT NULL, scope_id TEXT DEFAULT '',
  period TEXT DEFAULT 'day', limit_amount REAL DEFAULT 0,
  strategy TEXT DEFAULT 'downgrade',   -- downgrade | queue | pause
  enabled INTEGER DEFAULT 1, updated_at TEXT DEFAULT ''
);
```

P2 再加：`pipeline_steps`（DAG 节点/依赖/幂等键/产物）、`inspection_policy`（阈值/抽检率/升级模型/日预算）、`inspection_runs`（每批次的样本量、实际漏检、成本）。
P3（运营线）再加：`goals` / `journal` / `experiments`。

## 4. 关键流程

### 4.1 记账：一次调用一条，且幂等

调用点只有三处，统一走钩子（与 `loop._run_tool` 的 `on_tool` 同构，避免改动几十个工具）：

| 调用点 | 位置 | 记账字段 |
|---|---|---|
| 主回合 chat / stream | `AgentLoop` 拿到 `resp` 之后 | in/out tokens、cache hit、model |
| 压缩摘要 | `Compactor._summarize`（已记录 `_tokens`） | 同上，`kind=llm`，标记 `meta=compaction` |
| 视觉判定（P3） | 新增 vision adapter | images、模型、耗时 |

```python
amount = in_tokens/1000*in_price + out_tokens/1000*out_price \
       - cache_hit_tokens/1000*(in_price-cache_price)
db.record_usage(..., idem_key=f"{run_id}:{turn}:{call_seq}")
```

幂等键防止"重试/重放"导致重复计费——这在本项目不是假想：`run_retry` 与群组步级续跑都会重放调用。

### 4.2 预算闸门：三级、阶梯降级、绝不绕过护栏

超预算时的动作阶梯（可配）：`downgrade`（换更便宜的模型档）→ `queue`（排队到下一个周期）→ `pause`（停任务并通知人）。

两条硬约束：
1. **预算只影响"用不用贵的/要不要继续"，不能绕过任何安全护栏**（危险命令、越界路径、发布审批照旧）。
2. 每次降级/暂停都写审计（`cost:downgrade` / `cost:paused`），并进 run 摘要——否则又是一次"静音失败"。

### 4.3 模型分级路由（cascade）

给定 `quality_floor`（如"漏检率 ≤ 2%"）与任务预算：

```
先跑 cheap 档 → 置信度 < 阈值 或 复核不通过 → 升级 strong 档（最多 1 次）
期望成本 = cost(cheap) + p_fail × cost(strong)
若 期望成本 > 预算 或 p_fail 已被历史证伪 → 直接 strong
```

历史 `p_fail` 从账本与抽检结果里估（按 模型 × 任务类型 分组），不引入外部依赖。

### 4.4 抽检策略（检测场景的核心）

三件事，按顺序落地：

1. **阈值复核**：置信度 < `confidence_floor` 的样本 → 转人工（复用 `pending_decisions`，控制台「待决」页批准）或自动升级模型。
2. **分层抽检**：按批次风险估计（历史漏检率 + 本次低置信度比例）× 成本上限，动态决定抽检样本量（如每 50 件抽 2 件全流程复判）。
3. **反馈校正**：抽检发现的真实漏检数 → 修正下一批的策略参数，并记入 `inspection_runs`（简单在线反馈，不需要 RL）。

### 4.5 DAG 与断点续跑

`pipeline_steps(run_id, step_key, deps, status, attempt, idem_key, artifact)`：

- 幂等键 `idem_key = hash(run_id, step_key, input_digest)` → 重跑不重复计费、不重复写库；
- 断点续跑：进程重启后从第一个 `status != done` 的步骤开始（复用 `runs.prompt` 落库与 `run_retry`）；
- 并行度与 SLA：每步声明 `timeout` / `retries` / `parallel_group`。

## 6. 红线（工业场景不可妥协）

1. **不参与硬实时**：<100ms 的剔除/停机由边缘 PLC 做，DogBuddy 只做编排与复核，不进入控制闭环。
2. **LLM 不做像素级判定**：判定交给专用 CV 模型；LLM 负责调度、解释、写报告、异常归因。
3. **图像不出厂**：边缘只上行"图片引用 + 元数据"，原图留厂内；模型优先本地。
4. **花钱双闸门**：预算（自动）+ 单笔审批（人工，复用 `pending_decisions`）。
5. **全链路可追溯**：任一判定能回溯 图 → 模型版本 → 阈值 → 复核人 → 成本，1 分钟内查清。
6. **不静默降级**：预算降级、模型降档、复核跳过，都必须留审计与 run 摘要（这是本项目反复踩过的坑）。

## 8. 明确不做 / 已知风险

| 不做 | 原因 |
|---|---|
| 产线实时控制 | 硬实时要求 <100ms，且失效代价是停机/工伤，不该由 LLM 编排层承担 |
| LLM 直接判缺陷 | 像素级判定需要专用 CV 模型；LLM 的强项是调度、解释、报告 |
| 图片上云 | 工业客户几乎不接受；架构必须边缘优先 |
| "先建通用工业平台" | 同类项目最常见死法；先一条产线试点，拿到真实单位成本再扩 |

风险与缓解：

| 风险 | 缓解 |
|---|---|
| 单价配置错 → 决策错 | 单价改动全审计；`/healthz.costs` 与令牌用量对账（tokens × 单价 vs 账单） |
| 历史 `p_fail` 样本少 → 路由抖动 | 冷启动期只降档不升级，样本 ≥100 次后才开 cascade |
| 预算闸门误杀关键批次 | `pause` 前必须通知人；支持"本批次强制放行一次"（审计留痕） |
| 边缘设备不稳定 | 流水线必须可续跑（step checkpoint），不允许"从头再来" |
